The laboratory holds one demonstration for each algorithm that the encyclopedia teaches. Every demonstration is a sequence of steps: at each step a picture is drawn, and one sentence says what changed and why.

The pictures are not drawn by hand and they are not recorded. Each demonstration is produced by a trusted TypeScript reference implementation that lives with the algorithm it illustrates. The implementation runs, it reports every intermediate value, and the picture is generated from those values. The consequence is worth stating plainly: a demonstration cannot drift away from the algorithm, because the algorithm is what draws the picture.

The demonstrations are also deterministic. Nothing is random, nothing is timed, and no step depends on the order in which you press the buttons. The same input always produces the same trace, step for step, which is what makes the trace worth studying: the twentieth step is exactly the twentieth step every time.

The laboratory does not read your code. It runs the reference implementation on an input you choose, and shows you what that implementation does with it.

Every demonstration runs the algorithm of its article at the cost the article claims, so the picture and the complexity never disagree: a prefix sum is $O(1)$ once the totals are stored, a Fenwick tree answers a range in $O(\log n)$, and a table of ancestors is built in $O(n \log n)$.

## How to drive a demonstration

Every demonstration offers the same set of controls.

- **Play and pause** run the trace at the chosen speed, one step at a time.
- **Step forward and step backward** move a single step. Stepping backward is exact rather than approximate: every step carries the whole state that results from applying it, so the picture at step twenty is the picture at step twenty, not a replay of a recording.
- **Scrub** moves along the trace with the slider under the picture.
- **Speed** runs the trace at half speed, at normal speed, at twice the speed, or at four times the speed. The slow setting is the useful one for the structures with many steps, such as the knapsack table.
- **Presets** load a worked example. Each algorithm has two or three of them, chosen so that the interesting case is the one on display.
- **Custom input** lets you type your own instance and run it. The format is written under each demonstration below, and the demonstration refuses an input it cannot read, with a message that says what it wanted.
- **Annotations** toggle the labels that name the current operation. Turning them off leaves the picture alone.
- **Fullscreen** enlarges the picture to the size of the window, which is worth doing on the segment tree and the heavy-light decomposition.
- **Reset** restores the input of the selected preset.

## Keyboard shortcuts

| Key         | Action                 |
| ----------- | ---------------------- |
| Right arrow | Step forward one step  |
| Left arrow  | Step back one step     |
| Space       | Play or pause          |
| Home        | Jump to the first step |
| End         | Jump to the last step  |
| Escape      | Leave fullscreen       |

The shortcuts are ignored while the input box has the focus, so typing a space into the input never starts the trace.

## Reading the demonstrations

Each demonstration opens with a sentence that states the invariant the algorithm maintains, and each step after that says what changed and why it changed. The sentence under the picture is the narration of the step, and the chip beside it names the operation in the implementation that produced the step, such as `unite`, `compress-path`, `lift` or `point-update`. The chip is how a source listing and a picture are tied together: an implementation in any of the six languages marks the same operation in the same way, so the region of the code and the region of the picture are the same region of the algorithm.

The pictures never rely on color alone. A state that is drawn in gold also carries a label, and an edge that is drawn in a heavy stroke also carries the word that names it.

## The static fallback

Every laboratory has a storyboard: a short list of labeled frames that names what the picture holds at each stage of the demonstration. The article that introduces a laboratory writes the same account out in prose, so a reader whose browser refuses to run the script still gets the whole demonstration in words. The material is complete without JavaScript; only the motion is missing.

## What the laboratory does not do

The animation is an illustration, not a judge. It runs the reference implementation on an input you choose and shows you what that implementation does, so it cannot tell you whether the program you wrote is correct, and it does not accept a submission. The site has no service that runs code on your behalf; every value you see was computed in your browser by the reference implementation that ships with the article.

Use the picture to understand the algorithm. Write the code, and let the judge decide the code.

### Dijkstra's algorithm {#graphs.dijkstra}

Give one line per vertex in the form `u: v w`, where `w` is the weight of the edge. The priority queue holds the tentative distances.

<AlgorithmPlayer algorithm="graphs.dijkstra" />

### Disjoint set union {#graphs.dsu}

Give the number of elements on the first line, then one operation per line: `unite a b`, `find a` or `same a b`. The row of boxes is the parent array, and the forest underneath it is the partition.

<AlgorithmPlayer algorithm="graphs.dsu" />

### Prefix sums {#arrays.prefix-sums}

Give the values of the array on the first line, then one query per line in the form `left right`. Each box holds one running total, and the text under it names the array element that was added to reach it.

<AlgorithmPlayer algorithm="arrays.prefix-sums" />

### Fenwick tree {#range-queries.fenwick-tree}

Give the length of the array on the first line and its values on the second, then one operation per line: `add position delta`, `prefix position` or `range left right`. The boxes above the array are the blocks of the tree.

<AlgorithmPlayer algorithm="range-queries.fenwick-tree" />

### Segment tree {#range-queries.segment-tree}

Give the length of the array on the first line and its values on the second, then one operation per line: `set position value` or `range left right`. The tree underneath the array caches the sum of every range it covers.

<AlgorithmPlayer algorithm="range-queries.segment-tree" />

### 0/1 knapsack {#dynamic-programming.0-1-knapsack}

Give the capacity on the first line, then one line per item in the form `weight value`. The rows are the items in the order they are considered, and the columns are the budgets.

<AlgorithmPlayer algorithm="dynamic-programming.0-1-knapsack" />

### Convex hull trick {#dynamic-programming.convex-hull-trick}

Give one operation per line: `add slope intercept` adds a line, and `query point` asks for the smallest value at that point. The slopes must not decrease, and the points must not decrease either.

<AlgorithmPlayer algorithm="dynamic-programming.convex-hull-trick" />

### Lowest common ancestor {#trees.lca}

Give the tree in the form `root: child child`, then one query per line in the form `lca u v`. The number under a vertex is its depth, and the table of ancestors is what the jumps read.

<AlgorithmPlayer algorithm="trees.lca" />

### Heavy-light decomposition {#trees.heavy-light-decomposition}

Give the tree in the form `root: child child`, then one query per line in the form `path u v`. Every vertex carries the value one more than its number in the traversal order, and the number under a vertex is its position in the flattened array.

## Where to go next

A demonstration is the fastest way to see what an algorithm does, and it is not a substitute for the argument that it is correct. Each article in the [encyclopedia](/algorithms/) states the model, derives the update, proves the claim, and then shows the implementation in all six languages. Read the article first, and use the laboratory to check that the picture in your head matches the code on the page.
