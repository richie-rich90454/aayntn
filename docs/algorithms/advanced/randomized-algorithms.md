## At a glance

A randomized algorithm makes random choices while it runs. The input is fixed before those choices are made, so the analysis is an average over the algorithm's own coin flips rather than an assumption that the input is random. That distinction is the whole subject: a random pivot does not make the input easier, it makes the difficulty depend on chance instead of on the order the adversary chose.

There are two useful kinds of randomized algorithm. A Las Vegas algorithm always returns the correct answer, and only its running time is random. Randomized quicksort is the standard example: every pivot sequence sorts the array, while the comparison count depends on the pivots. A Monte Carlo algorithm runs in a fixed or bounded time and may return a wrong answer with some probability. Sampling a few positions to find a frequent value is the standard example. The two require different promises. A Las Vegas algorithm is judged by its expected time and its worst-case time. A Monte Carlo algorithm is judged by its running time and by the probability that its answer is wrong.

This article uses randomized quicksort as the running example. It chooses a pivot uniformly from the current interval, partitions the interval into values below, equal to, and above the pivot, and recurses on the two outer blocks. The expected comparison count is $O(n \log n)$ and the worst case is $O(n^2)$. The three-way partition costs nothing extra and removes the duplicate-heavy input that makes a two-way partition quadratic. The reference programs use a xorshift32 generator seeded with 2463534242 so that all six languages take the same pivots, produce the same sorted array, and report the same comparison count; the fixed seed is a testing decision, not a claim that a fixed seed is safe against an adversary.

## Problem motivation

Quicksort is the default sorting algorithm because its inner loop is fast and its memory access is sequential. The standard deterministic version picks the last element, the first element, or the median of three fixed positions. Each of those rules has an input that makes it quadratic. With the last element as the pivot, an already sorted array is the worst case: every partition removes one element and the comparison count is $n + (n - 1) + \cdots + 1 = n(n-1)/2$. With the median of three on the first, middle, and last positions, an adversary who knows the rule can build an input that keeps the median at an extreme of every interval.

That is not a theoretical curiosity. Real inputs are often sorted, nearly sorted, or generated by a process that correlates with the pivot rule. A submission that is fast on random tests and quadratic on the official tests is a common way to lose a contest. The median-of-three rule removes the accidental sorted cases but not the deliberate ones.

A random pivot removes the adversary's leverage. The input is fixed, but the pivot positions are chosen after the input arrives and are not known to the person who built the tests. A bad split is still possible; it is simply unlikely, and the probability can be bounded without knowing anything about the input distribution. The expected comparison count is $O(n \log n)$ for every input, and the probability of a quadratic run is astronomically small.

The same idea applies outside sorting. A value that occurs in more than one fifth of a range is held by a random position of that range with probability above one fifth, so a few dozen samples find it even when the array is enormous. The smallest enclosing circle of a point set can be built by inserting the points in random order, which makes the expected number of boundary changes linear. A treap assigns random priorities to the keys of a binary search tree and keeps the tree balanced in expectation. Randomized hashing chooses the hash function after the input is known, which removes the fixed collisions that an adversary can build against a published function.

The price is always the same: the guarantee becomes probabilistic. A judge can run the program once and be unlucky. A real-time system cannot accept a worst case that is merely unlikely. A reproducible test suite needs a fixed seed, and a fixed seed can be read by an adversary. Randomized algorithms are the right tool when the worst case is rare enough to ignore, and the wrong tool when the worst case is the requirement.

## Recognition patterns

Randomized algorithms show up when the statement asks for an expected bound, a high-probability bound, or a result that can be verified after it is guessed. The following phrases are strong signals.

- "Expected $O(n \log n)$", "in expectation", "with high probability", "with probability at least $1 - 1/n$".
- "The input may be adversarial", "the tests are adaptive", "no deterministic solution is known".
- "Choose a random element", "sample a position", "shuffle the array", "assign random priorities".
- "Find any value that occurs more than", "the majority element", "a value that appears frequently".
- "The answer can be verified in polynomial time", which is the signature of a Monte Carlo search.
- "The order of the input is irrelevant", which suggests that shuffling it costs nothing.
- The names treap, skip list, randomized incremental construction, reservoir sampling, and polynomial hashing.

The constraint values decide whether randomization is worth the loss of a hard guarantee.

| Situation | What it suggests |
| --- | --- |
| Sorting $10^5$ to $10^7$ values, adversarial tests possible | Randomized quicksort, or introsort with a heap fallback |
| Exactly one order statistic, no need for the full order | Randomized quickselect |
| Millions of values, only frequent values matter | Random sampling with deterministic verification |
| A geometric structure built incrementally | Random insertion order |
| A balanced search tree with split and merge | Treap with random priorities |
| A hash table that must resist crafted collisions | Randomized hashing |
| Hard real-time deadline | A deterministic worst-case algorithm |
| Tiny input, $n \le 100$ | Any correct sort; the pivot rule is irrelevant |
| The judge demands exact reproducibility | A fixed seed, with the adversarial risk stated |
| The answer cannot be checked cheaply | Monte Carlo is dangerous; prefer Las Vegas |

The last row is the one that catches people. A Monte Carlo algorithm is only useful when a candidate answer can be verified independently. Sampling a frequent value works because the count of the sampled value can be computed exactly. Sampling a divisor in the Ghd problem works because divisibility can be checked exactly. A random guess that cannot be checked is not an algorithm, it is a lottery.

## Naive approach

The deterministic baseline picks the last element as the pivot and uses a two-way partition.

```cpp
void quicksort(std::vector<int>& a, int lo, int hi) {
    if (lo >= hi) return;
    int pivot = a[hi];
    int i = lo;
    for (int j = lo; j < hi; ++j) {
        if (a[j] < pivot) {
            std::swap(a[i], a[j]);
            ++i;
        }
    }
    std::swap(a[i], a[hi]);
    quicksort(a, lo, i - 1);
    quicksort(a, i + 1, hi);
}
```

This is correct and short. On a sorted array it performs $n(n-1)/2$ comparisons, because every partition puts the pivot at the front of its interval and the next interval is everything to the right. On an array of equal values it does the same, because the strict comparison sends every equal value to the right. The recursion depth is $n$ in both cases, which is a second failure: a C or C++ program can exhaust an 8 MB stack at around $10^5$ frames, and Java and JavaScript hit their limits earlier.

The second baseline shuffles the array with Fisher-Yates and then runs the deterministic last-element quicksort.

```cpp
for (int i = n - 1; i > 0; --i) {
    int j = random_below(i + 1);
    std::swap(a[i], a[j]);
}
quicksort(a, 0, n - 1);
```

The shuffle makes the pivot a uniformly random element of the original array, so the expected comparison count is $O(n \log n)$ for every input. The duplicate problem remains: an all-equal array is still quadratic, because the two-way partition puts every equal value on one side of the pivot. The shuffle also costs $n$ random draws and $n$ swaps before the sort starts, and it destroys the original order, which the caller may need.

The third baseline is the standard library sort. C++ `std::sort` is introsort: quicksort with a median-of-three pivot, a depth limit, and a heapsort fallback when the recursion gets too deep. Java sorts primitives with a dual-pivot quicksort and objects with a stable merge sort. Those routines are excellent defaults, and a contest solution should usually call them unless the problem is about the sort itself. The reason to write randomized quicksort is to understand the partition, to control the comparison count, or to answer a problem whose structure needs a custom pivot.

The naive and standard routines are also the reference implementations for a differential test. A randomized sort must agree with `std::sort` on every input, and the comparison count must agree across the six language variants when the generator is fixed.

## Key insight

The insight is that a uniformly random pivot makes the split balanced with constant probability, no matter how the input is ordered.

Consider an interval of $m$ values. The pivot's rank inside the interval is uniform from $1$ to $m$. With probability at least $1/2$, the rank lies in the middle half of the interval, between $m/4$ and $3m/4$. In that case both sides have at most $3m/4$ values, so the next interval is at most three quarters of the current one. A path down the recursion tree therefore shrinks geometrically, and its expected length is $O(\log n)$.

The second insight is that the three-way partition makes duplicates disappear as a block. A two-way partition around a pivot value $p$ sends every value equal to $p$ to one side, so the next interval still contains all of them. An all-equal array then removes one element per round. A three-way partition groups the values below $p$, the values equal to $p$, and the values above $p$. The middle block is already in its final position, so both recursive calls exclude it. An all-equal array finishes in one partition with $n$ comparisons and no recursive work.

The third insight is that the random choices are independent of the input. The analysis does not need a distribution on the input, only the distribution of the pivot ranks. That is why the expected bound holds for every fixed array, including the arrays that defeat every deterministic rule. The adversary chooses the input before the coin flips, and the expectation is over the coin flips.

The fourth insight is that a fixed seed is a testing device, not a security device. With a fixed seed, the pivot sequence is a deterministic function of the input size and the previous pivots. An adversary who reads the source can construct an input that follows the bad branch at every step. A contest submission therefore seeds from a source the tests cannot predict, while a reference implementation seeds from a constant so that the six languages can be compared byte for byte.

## Visual intuition

Picture the current interval as a row of values. The generator picks one position, its value becomes the pivot $p$, and one pass rearranges the row into three blocks.

| Left block           | Equal block               | Right block             |
| -------------------- | ------------------------- | ----------------------- |
| values less than $p$ | values equal to $p$       | values greater than $p$ |
| recursed on          | already in final position | recursed on             |

The equal block is the part that a two-way partition does not isolate. In a three-way partition, every copy of the pivot lands there, and the next level of recursion sees only the two outer blocks.

For the array $[5, 3, 8, 1, 4]$, the first generator value is $723471715$. The interval is $[0, 4]$, so the pivot index is $723471715 \bmod 5 = 0$ and the pivot is $5$. The partition produces:

| Step  | Array             | Left boundary | Cursor | Right boundary | Action  |
| ----- | ----------------- | ------------- | ------ | -------------- | ------- |
| Start | $[5, 3, 8, 1, 4]$ | 0             | 0      | 4              | $5 = 5$ |
| 1     | $[5, 3, 8, 1, 4]$ | 0             | 1      | 4              | $3 < 5$ |
| 2     | $[3, 5, 8, 1, 4]$ | 1             | 2      | 4              | $8 > 5$ |
| 3     | $[3, 5, 4, 1, 8]$ | 1             | 2      | 3              | $4 < 5$ |
| 4     | $[3, 4, 5, 1, 8]$ | 2             | 3      | 3              | $1 < 5$ |
| 5     | $[3, 4, 1, 5, 8]$ | 3             | 4      | 3              | Done    |

The equal block is position $3$. The left interval is $[0, 2]$ and the right interval is $[4, 4]$. The right interval has one element, so it is already sorted. The left interval is partitioned again.

The recursion tree has one node per partition:

```text
[0, 4], pivot 5, 5 comparisons
  [0, 2], pivot 4, 3 comparisons
    [0, 1], pivot 3, 2 comparisons
      [0, 0]
      [1, 1]
  [4, 4]
```

The total is $5 + 3 + 2 = 10$ comparisons. A balanced tree would have about $n \log_2 n$ comparisons; this tree is slightly better than the average for five elements, because the first pivot landed at the median of the array.

The unbalanced picture is the same row with a pivot that is always the minimum. The equal block is the first position, the left interval is empty, and the right interval contains everything else. The row shrinks by one position per level, the tree becomes a path of length $n$, and the comparison count becomes quadratic.

## Formal model

Let $A = (a_0, a_1, \ldots, a_{n-1})$ be an array of $n$ signed 32-bit integers.

::: math definition Definition
A Las Vegas algorithm always returns a correct answer and has a random running time. A Monte Carlo algorithm has a deterministic or bounded running time and returns a correct answer with probability at least $1 - \delta$, for a stated error probability $\delta$.
:::

::: math definition Definition
The xorshift32 generator maintains a 32-bit state $x$. Starting from a nonzero seed $x_0$, it applies

$$
x \leftarrow x \oplus (x \ll 13), \qquad
x \leftarrow x \oplus (x \gg 17), \qquad
x \leftarrow x \oplus (x \ll 5),
$$

where every operation is reduced modulo $2^{32}$ and $\gg$ is a logical right shift. The reference seed is $x_0 = 2463534242$.
:::

::: math definition Definition
A three-way partition of the interval $[lo, hi]$ around a value $p$ returns boundaries $lt \le gt$ such that, after the partition,

$$
a_i < p \text{ for } lo \le i < lt, \qquad
a_i = p \text{ for } lt \le i \le gt, \qquad
a_i > p \text{ for } gt < i \le hi.
$$

The interval $[lt, gt]$ is the equal block.
:::

::: math definition Definition
The comparison count of a run is the number of times the partition loop examines an element against the pivot. Each examination counts once, whether the element is below, equal to, or above the pivot.
:::

The generator is not a source of cryptographic randomness. Its state space is $2^{32} - 1$ nonzero states, its period is $2^{32} - 1$ for the standard shift constants, and its low bits are weaker than its high bits. It is chosen because it is short, fast, and easy to reproduce in six languages, which is exactly what a reference implementation needs.

::: math lemma Lemma
After a three-way partition around $p$, the sorted order of the interval is the left block, then the equal block, then the right block.
:::

::: math proof Proof
Every value in the left block is strictly less than $p$, every value in the equal block is $p$, and every value in the right block is strictly greater than $p$. Therefore every left value precedes every equal value and every equal value precedes every right value in non-decreasing order. The left block occupies sorted positions $lo$ through $lt - 1$, the equal block occupies $lt$ through $gt$, and the right block occupies the rest. $\square$
:::

::: math lemma Lemma
The three-way partition removes at least one element from the recursion, and both recursive intervals are strictly shorter than the current interval.
:::

::: math proof Proof
The pivot is copied from an element of the interval, so the equal block contains at least that element and is non-empty. The recursive calls use $[lo, lt-1]$ and $[gt+1, hi]$, both of which exclude the non-empty equal block, so both have length at most $hi - lo$. $\square$
:::

The model has one more quantity that matters for the expected analysis: the rank of the pivot. If the current interval has $m$ elements and the pivot index is uniform over the interval, the pivot's sorted rank inside the interval is uniform from $1$ to $m$. The reference computes the index as $lo + (x \bmod m)$, where $x$ is the next generator value. The modulo operation is not perfectly uniform when $m$ does not divide $2^{32}$, but the bias is at most $m/2^{32}$, which is below one part in $10^5$ for every $m$ that fits in memory. The analysis treats the pivot as uniform; a rigorous implementation that needs exact uniformity uses rejection sampling.

## Algorithm derivation

The algorithm is a recursive divide-and-conquer with a random pivot and a three-way partition.

1. If the interval has at most one element, return.
2. Draw the next 32-bit value and reduce it modulo the interval length to get a pivot index.
3. Copy the pivot value before changing the array.
4. Partition the interval into values below, equal to, and above the pivot.
5. Recurse on the left block and the right block, in that order.

```cpp
void randomized_quicksort(std::vector<int>& a, int lo, int hi) {
    if (lo >= hi) return;

    int pivot = a[lo + static_cast<int>(next_random() % static_cast<unsigned>(hi - lo + 1))];
    int lt = lo;
    int i = lo;
    int gt = hi;

    while (i <= gt) {
        ++comparisons;
        if (a[i] < pivot) {
            std::swap(a[lt], a[i]);
            ++lt;
            ++i;
        } else if (a[i] > pivot) {
            std::swap(a[i], a[gt]);
            --gt;
        } else {
            ++i;
        }
    }

    randomized_quicksort(a, lo, lt - 1);
    randomized_quicksort(a, gt + 1, hi);
}
```

The order of the recursive calls is part of the observable behavior when the generator is fixed. The listings always recurse on the left block first and the right block second, so the sequence of generator draws is the preorder traversal of the recursion tree. Changing the order changes the pivots and the comparison count, even though the sorted output stays the same.

The partition loop maintains three regions. Positions before `lt` hold values below the pivot. Positions from `lt` to `i - 1` hold values equal to the pivot. Positions after `gt` hold values above the pivot. The cursor `i` examines the unclassified middle. A value below the pivot is swapped into the first equal position, which extends the left region and shifts the equal region right by one. A value above the pivot is swapped with the value at `gt`, which extends the right region; the value that arrives at `i` has not been examined, so `i` stays. A value equal to the pivot simply extends the equal region.

The algorithm terminates because every partition removes the non-empty equal block from both recursive intervals. The recursion reaches intervals of length zero or one, which are sorted by definition. The generator can return any sequence, including a sequence that always chooses the minimum, so the correctness argument cannot depend on the randomness. It only depends on the partition and the recursion.

The generator itself is a few lines:

```cpp
std::uint32_t next_random() {
    std::uint32_t x = rng_state;
    x ^= x << 13;
    x ^= x >> 17;
    x ^= x << 5;
    rng_state = x;
    return x;
}
```

In C and C++, the unsigned 32-bit type supplies the modulo $2^{32}$ arithmetic automatically. In Java, the state is an `int`, the right shift is `>>>`, and the index computation masks the state with `0xFFFFFFFFL` before the modulo. In Python, Pascal, and JavaScript, each left shift must be masked because those languages have wider integers. Those details are not cosmetic: if one language masks differently, its generator produces a different sequence, and the comparison counts diverge even though every language still sorts correctly.

## Step-by-step execution

Use the fixture array $[5, 3, 8, 1, 4]$. The generator produces $723471715$, $2497366906$, and $2064144800$ for the three partitions.

**First partition.** The interval is $[0, 4]$ and the pivot index is $723471715 \bmod 5 = 0$, so the pivot is $a_0 = 5$.

| Step  | Array             | `lt` | `i` | `gt` | Comparison | Action               |
| ----- | ----------------- | ---- | --- | ---- | ---------- | -------------------- |
| Start | $[5, 3, 8, 1, 4]$ | 0    | 0   | 4    | 1          | $5 = 5$              |
| 1     | $[5, 3, 8, 1, 4]$ | 0    | 1   | 4    | 2          | $3 < 5$              |
| 2     | $[3, 5, 8, 1, 4]$ | 1    | 2   | 4    | 3          | $8 > 5$              |
| 3     | $[3, 5, 4, 1, 8]$ | 1    | 2   | 3    | 4          | $4 < 5$              |
| 4     | $[3, 4, 5, 1, 8]$ | 2    | 3   | 3    | 5          | $1 < 5$              |
| Done  | $[3, 4, 1, 5, 8]$ | 3    | 4   | 3    |            | Equal block $[3, 3]$ |

The equal block is position $3$. The left interval is $[0, 2]$ and the right interval is $[4, 4]$. The right interval is a single element and returns without a draw.

**Second partition.** The interval is $[0, 2]$. The next generator value is $2497366906$, and $2497366906 \bmod 3 = 1$, so the pivot is $a_1 = 4$.

| Step  | Array       | `lt` | `i` | `gt` | Comparison | Action               |
| ----- | ----------- | ---- | --- | ---- | ---------- | -------------------- |
| Start | $[3, 4, 1]$ | 0    | 0   | 2    | 1          | $3 < 4$              |
| 1     | $[3, 4, 1]$ | 1    | 1   | 2    | 2          | $4 = 4$              |
| 2     | $[3, 4, 1]$ | 1    | 2   | 2    | 3          | $1 < 4$              |
| Done  | $[3, 1, 4]$ | 2    | 3   | 2    |            | Equal block $[2, 2]$ |

The left interval is $[0, 1]$ and the right interval is empty.

**Third partition.** The interval is $[0, 1]$. The next generator value is $2064144800$, and $2064144800 \bmod 2 = 0$, so the pivot is $a_0 = 3$.

| Step  | Array    | `lt` | `i` | `gt` | Comparison | Action               |
| ----- | -------- | ---- | --- | ---- | ---------- | -------------------- |
| Start | $[3, 1]$ | 0    | 0   | 1    | 1          | $3 = 3$              |
| 1     | $[3, 1]$ | 0    | 1   | 1    | 2          | $1 < 3$              |
| Done  | $[1, 3]$ | 1    | 2   | 1    |            | Equal block $[1, 1]$ |

The left interval is $[0, 0]$ and the right interval is empty. The recursion is finished. The sorted array is $[1, 3, 4, 5, 8]$, and the comparison count is $5 + 3 + 2 = 10$.

The duplicate fixture $[2, 2, 1, 1, 3, 3]$ shows why the three-way block matters. The first pivot is $2$, and the first partition moves both copies of $1$ to the left and both copies of $2$ into the equal block in one pass. The two remaining intervals are $[1, 1]$ and $[3, 3]$, each of which is one partition of two equal values. The total is $6 + 2 + 2 = 10$ comparisons, with no repeated comparisons of the duplicated pivot.

The single-element fixture $[7]$ returns immediately, performs no generator draw, and reports zero comparisons. That is the edge case: a correct program must not read a pivot from an empty interval or call the generator when there is nothing to partition.

## Correctness proof

::: math theorem Theorem
For every array of $n$ integers and every seed, the randomized quicksort returns the values in non-decreasing order.
:::

::: math proof Proof
The proof is by induction on the interval length. The base case is an interval of length zero or one, which is already sorted.

For an interval of length $m \ge 2$, the algorithm chooses a pivot from the interval, so the pivot is one of the values. By the partition lemma, the interval is rearranged into a left block of values below the pivot, an equal block of values equal to the pivot, and a right block of values above the pivot. Every value in the left block is at most every value in the equal block, and every value in the equal block is at most every value in the right block.

The two recursive calls sort the left and right blocks by the induction hypothesis, because both blocks are strictly shorter than the current interval. Concatenating the sorted left block, the untouched equal block, and the sorted right block gives a non-decreasing order of the whole interval.

The argument never uses a property of the generator. Any pivot sequence produces a valid pivot from the current interval, and the partition always removes the equal block, so the recursion terminates and the concatenation is sorted. $\square$
:::

The theorem is the Las Vegas guarantee: the output is correct for every seed. The randomness affects only how many comparisons the run performs and how deep the recursion goes.

The Monte Carlo side needs a separate argument, because a sampled algorithm can be wrong. The pattern is always the same: sample a candidate, verify it deterministically, and bound the probability that the sampling misses every correct candidate. A verified candidate is never wrong; the only failure is a missed candidate. That separation is what makes a Monte Carlo algorithm usable.

## Complexity analysis

| Method | Comparisons | Extra space |
| --- | --- | --- |
| Deterministic last-pivot quicksort, sorted input | $n(n-1)/2$ | $O(n)$ stack |
| Deterministic last-pivot quicksort, random input | $O(n \log n)$ expected over the input | $O(\log n)$ expected stack |
| Shuffle, then last-pivot quicksort | $O(n \log n)$ expected | $O(\log n)$ expected stack |
| Randomized three-way quicksort | $O(n \log n)$ expected | $O(\log n)$ expected stack |
| Randomized three-way quicksort, worst case | $O(n^2)$ | $O(n)$ stack |
| Standard library introsort | $O(n \log n)$ worst case | $O(\log n)$ stack |

The expected comparison bound follows from linearity of expectation over pairs of elements. Sort the array conceptually, break ties arbitrarily, and number the elements by their final positions. Two elements at final positions $i < j$ are compared exactly when the first pivot chosen from the set of elements between them, inclusive, is one of the two. With a uniform pivot, that first pivot is uniform over the $j - i + 1$ candidates, so the probability is $2/(j - i + 1)$. Summing over all pairs,

$$
\sum_{1 \le i < j \le n} \frac{2}{j - i + 1}
= 2 \sum_{d=1}^{n-1} \frac{n - d}{d + 1}
< 2n \sum_{d=1}^{n} \frac{1}{d}
= O(n \log n).
$$

The three-way partition can only reduce the count, because it removes every copy of the pivot at once; the two-way bound is therefore an upper bound for the three-way version as well.

The expected recursion depth follows from the middle-half argument. At an interval of length $m$, the pivot rank is in the middle half with probability at least $1/2$, and then both children have length at most $3m/4$. A path that waits for such a pivot shrinks by a constant factor every expected two levels, so its expected length is $O(\log n)$. The worst case is a path of length $n$, which happens when every pivot is the minimum or the maximum of its interval.

The worst-case comparison count is $n(n-1)/2$. The probability of that particular pivot sequence is negligible, but it is not zero. A program that must guarantee $O(n \log n)$ in the worst case uses introsort: it counts the recursion depth and switches to heapsort when the depth exceeds $2 \log_2 n$. That fallback preserves the randomized speed on ordinary inputs and supplies a deterministic worst-case bound.

The space is the array plus the recursion stack. The array is $O(n)$ and is sorted in place. The stack is $O(\log n)$ in expectation and $O(n)$ in the worst case. The generator is constant space, and the comparison counter is one machine word. A 32-bit counter can overflow at $n$ around $10^5$ in the quadratic case, so the listings use a 64-bit counter or a Python integer.

The generator costs one multiply-free sequence of shifts and exclusive-ors per partition. There are at most $n$ partitions, so the generator adds $O(n)$ time, which is below the comparison bound. The modulo operation is a division; on most hardware it costs a few cycles and is negligible compared with the partition's memory traffic.

| The problem is the sort itself, or the pivot rule matters | Randomized quicksort |
| Duplicate-heavy values | Three-way randomized quicksort |
| A guaranteed $O(n \log n)$ worst case | Mergesort, heapsort, or introsort |
| Stable order required | Mergesort |
| One order statistic, no full order | Randomized quickselect |
| Many frequent-value queries over a static array | Random sampling plus exact counts, or a deterministic range structure |
| A balanced tree with split and merge | Treap |
| Collision-resistant hashing against an adversary | Randomized hashing |
| A geometric structure built from points | Randomized incremental construction |
| A hard real-time deadline | A deterministic algorithm with a proven worst case |
| Tiny input | Any correct sort; do not add machinery |

The first two rows are the practical distinction. In a contest, `std::sort` is almost always the right choice; writing quicksort by hand is justified when the problem asks for a comparison count, a custom comparator, a partial sort, or a partition that becomes part of a larger algorithm. Randomized quicksort is also a teaching tool: it is the shortest complete example of a Las Vegas algorithm with a nontrivial analysis.

The rows involving sampling need a verification step. A random sample of positions is not an answer; it is a candidate. The answer is the candidate whose exact count passes the threshold. If the verification is expensive, the sampling may not pay for itself. If the verification is impossible, the algorithm is a guess.

The last row is the one that saves contests. At $n \le 100$, a quadratic insertion sort is faster than quicksort in practice, and the random pivot adds a generator call to every partition. The asymptotic advantage of randomization only appears when the input is large enough for the bad case to matter.

## Reference implementations

The six `program` variants published by the manifest implement one contract:

1. Read $n$.
2. Read $n$ signed 32-bit integers.
3. Sort them with randomized quicksort and a three-way partition.
4. Print the sorted values on one line, separated by single spaces.
5. Print the number of pivot comparisons on the next line.

The input is whitespace-separated, so a line break may appear anywhere between two numbers. Every variant uses the same xorshift32 generator, the same seed, the same pivot formula, the same three-way partition, and the same left-then-right recursion order. The six outputs are therefore byte-identical on the shared fixtures, including the comparison count.

The variants differ only in storage, integer width, and input handling.

- The C variant keeps the generator state in a `uint32_t`, so the shifts wrap at 32 bits with no explicit mask. It allocates the array on the heap, frees it on every exit path, and uses a `long long` comparison counter.
- The C++17 variant keeps the state in `std::uint32_t` and the array in a `std::vector<int>`. It uses references for the swaps and deliberately does not call `std::sort`, because the partition is the subject.
- The Java variant keeps the state in an `int`, uses the logical right shift `>>>`, and masks the state with `0xFFFFFFFFL` before the modulo. The source is `java/Main.java` and the class is `Main`, so the judge entry point is the standard one. A byte-buffer scanner avoids the per-token cost of `java.util.Scanner`.
- The Python variant reads all of standard input once and splits it. It masks every left shift with `0xFFFFFFFF`, which reproduces the 32-bit wrap exactly. Python integers do not overflow, but the comparison counter follows the same sequence as the compiled languages.
- The Pascal variant uses `Int64` for the generator state and the counter, reads one argument per `Read`, uses `SysUtils`, and avoids `IOResult` so it stays inside the subset that the browser-based compiler accepts. It masks with a typed `Int64` constant initialized from `$FFFFFFFF`; an untyped `$FFFFFFFF` in the expression is sign-extended by this compiler and would produce a different sequence, which is exactly the kind of cross-language divergence the fixed seed is meant to catch.
- The JavaScript variant is an ES module, so it imports `readFileSync` rather than calling `require`. It applies `>>> 0` after every generator step to keep the state an unsigned 32-bit Number. It is an educational reference, not a USACO submission language.

The comparison count is defined precisely: one increment per iteration of the partition loop, before the branch that classifies the element. A two-way partition that tests `<` and then `>` would count two comparisons for an equal element; the listings avoid that ambiguity by counting one examination per element. The count is part of the output because it makes the randomized behavior visible and because it lets a reader compare pivot rules without instrumenting the code.

The manifest publishes no `minimal` variant. A reusable sort class would hide the partition, the generator, and the comparison counter, which are the three things the article is about. The `program` variants are the complete statement of the algorithm.

## Recursion decision

Randomized quicksort is naturally recursive: partition, then sort the two outer blocks. The recursion depth is the height of the partition tree, which is $O(\log n)$ in expectation and $O(n)$ in the worst case.

| Language | Default limit | Practical depth | Recommendation |
| --- | --- | --- | --- |
| C and C++ | 8 MB of stack | About $10^5$ frames | Recursion is fine for expected depth; use introsort for a hard bound |
| Java | 512 KB to 1 MB per thread | About $10^4$ frames | Recursion is fine; raise the stack only if the input is adversarial |
| Python | Interpreter limit of 1000 | 1000 frames | Raise the limit for large inputs, or use an explicit stack |
| Pascal | The operating system stack | Depends on the platform | Recursion is fine for expected depth |
| JavaScript | The V8 engine limit | About $10^4$ frames | Recursion is fine for expected depth |

The listings recurse on the left block and then the right block. That order is what makes the generator sequence reproducible, but it does not guarantee a small stack. A production sort can recurse on the smaller block and loop on the larger one:

```cpp
while (lo < hi) {
    int lt, gt;
    partition(a, lo, hi, lt, gt);
    if (lt - lo < hi - gt) {
        randomized_quicksort(a, lo, lt - 1);
        lo = gt + 1;
    } else {
        randomized_quicksort(a, gt + 1, hi);
        hi = lt - 1;
    }
}
```

The smaller-side-first rule caps the stack at $O(\log n)$ even in the worst case, because every recursive call is on an interval of at most half the current size. It changes the order in which the generator is consumed, so it changes the comparison count; that is acceptable when reproducibility is not required. It is the standard way to make quicksort safe on a memory-constrained judge without giving up the expected bound.

An explicit stack removes the language recursion limit entirely, but it replaces two clear recursive calls with a manual push and pop. It is worth the code when the input can be adversarial and the language has a low frame limit, especially Python and JavaScript.

## Implementation walkthrough

Five details decide whether the six implementations agree.

The 32-bit wrap must be explicit in every language that has wider integers. C and C++ get it from `uint32_t`. Java gets it from `int` plus `>>>`. Python, Pascal, and JavaScript must mask after every left shift. In Pascal, the mask must be a typed `Int64` constant initialized from `$FFFFFFFF`; an untyped hexadecimal literal in the expression is treated as a signed 32-bit value in this compiler and sign-extends to `-1`, which turns the mask into a no-op. That single mistake changed the first fixture's comparison count from 10 to 11 while still producing a correctly sorted array, which is why the count is part of the output.

The pivot value must be copied before the partition. The partition moves the element that supplied the pivot, so reading `a[pivot_index]` after the first swap returns an unrelated value. Every listing stores the pivot in a local before entering the loop.

The pivot index must use the inclusive length. The interval $[lo, hi]$ has $hi - lo + 1$ positions. Omitting the plus one never selects the last position, which biases the pivot toward the front and can turn a sorted input into a slow sequence. The modulo must be applied to the unsigned 32-bit value, not to a sign-extended integer.

The two branches of the three-way partition are not symmetric. A value below the pivot is swapped with the first equal position, and both boundaries advance, because the value that arrives at the cursor is a copy of the pivot. A value above the pivot is swapped with the last unclassified position, and only the right boundary moves, because the value that arrives at the cursor has not been examined. Advancing the cursor in that branch skips an element and can leave a smaller value on the wrong side of the pivot.

The comparison counter must be wide enough. A 32-bit signed counter overflows after about $2.1 \ast 10^9$ comparisons, which a quadratic run reaches at $n$ around $6.5 \ast 10^4$. The C and C++ listings use `long long`, Java uses `long`, Pascal uses `Int64`, and Python uses an arbitrary-precision integer. JavaScript uses a Number, which is exact up to $2^{53}$, far beyond any feasible comparison count.

A compact Python core is:

```python
def randomized_quicksort(a, lo, hi):
    global comparisons
    if lo >= hi:
        return
    pivot = a[lo + next_random() % (hi - lo + 1)]
    lt, i, gt = lo, lo, hi
    while i <= gt:
        comparisons += 1
        if a[i] < pivot:
            a[lt], a[i] = a[i], a[lt]
            lt += 1
            i += 1
        elif a[i] > pivot:
            a[i], a[gt] = a[gt], a[i]
            gt -= 1
        else:
            i += 1
    randomized_quicksort(a, lo, lt - 1)
    randomized_quicksort(a, gt + 1, hi)
```

The function mutates the array in place, which is the price of $O(1)$ extra storage per frame. A caller that needs the original order must pass a copy.

## Common mistakes

| Mistake | What happens | How to avoid |
| --- | --- | --- |
| Different generator constants per language | The sorted arrays agree but the comparison counts differ | Use the same shift constants and the same seed everywhere |
| A mask that sign-extends | The generator sequence diverges silently | Use an unsigned type, or a typed `$FFFFFFFF` constant |
| Pivot read after the first swap | The partition uses a value that is no longer at the pivot position | Copy the pivot before the loop |
| Pivot index uses `hi - lo` | The last position is never chosen, and the pivot is biased | Use `hi - lo + 1` |
| Advancing after a `>` swap | An unexamined value is skipped and can land on the wrong side | Decrement `gt` and leave `i` alone |
| Two-way partition on all-equal input | $n(n-1)/2$ comparisons and $n$ stack frames | Use the three-way partition |
| Claiming $O(n \log n)$ worst case | A crafted input can still be quadratic | State expected time, or use introsort |
| A fixed seed in a submitted solution | An adversary can precompute the bad input | Seed from an unpredictable source |
| A 32-bit comparison counter | Overflow on a quadratic run | Use a 64-bit counter |
| Trusting a Monte Carlo candidate | A wrong answer with no error signal | Verify every candidate deterministically |

### Why this fails: the skipped value after a `>` swap

The plausible wrong partition advances the cursor after every swap, because the loop looks like a standard two-pointer pass. The smallest counterexample is the array $[2, 3, 1]$ with the pivot $2$.

The cursor starts at position $0$, which holds $2$ and is equal to the pivot, so it advances. Position $1$ holds $3$, which is greater than the pivot, so it is swapped with the last unclassified value $1$. The array becomes $[2, 1, 3]$ and the right boundary moves to position $1$. If the cursor also advances to position $2$, it is now past the right boundary, so the loop ends. The value $1$ has never been examined, and it sits to the right of the pivot even though it is smaller. The partition reports the equal block as position $0$ and the right block as positions $1$ through $2$. The recursive call sorts $[1, 3]$ but cannot move the $1$ to the left of the $2$, so the final array is $[2, 1, 3]$, which is not sorted.

The correct branch leaves the cursor at position $1$ and examines the newly arrived $1$, swaps it into the left block, and only then advances. The array becomes $[1, 2, 3]$. The bug is subtle because the array length is only three and the wrong result still contains the same values; a test that checks the multiset but not the order finds nothing.

### Why this fails: the mask that is not a mask

A second failure is specific to languages whose integers are wider than 32 bits. In Pascal, the natural translation of the C generator is:

```pascal
RngState := (RngState xor ((RngState shl 13) and $FFFFFFFF)) and $FFFFFFFF;
```

In this compiler, `$FFFFFFFF` is a signed 32-bit constant with the value $-1$. It sign-extends to the 64-bit `Int64` state, so `and $FFFFFFFF` leaves every bit unchanged. The state grows beyond 32 bits, the right shift is no longer the logical 32-bit shift, and the generator produces a different sequence. The first fixture still sorts correctly, because every pivot is still a valid element, but it reports 11 comparisons instead of 10. The six-language differential test catches the mistake immediately, and the comparison count is the signal that the generators diverged.

The fix is to use an unsigned 32-bit type where the language has one, or a typed `Int64` constant initialized from `$FFFFFFFF`. The typed constant is evaluated once at compile time as $4294967295$, while the bare literal in the expression is sign-extended. A bare hexadecimal literal needs that constant or an equivalent unambiguous declaration.

### Why this fails: the all-equal input

A two-way partition with a strict comparison sends every equal value to the same side as the values above the pivot. On an array of $n$ equal values, every partition removes one element, so the comparison count is $n(n-1)/2$ and the recursion depth is $n$. At $n = 10^5$, that is about $5 \ast 10^9$ comparisons and a stack overflow long before the count finishes. The three-way partition groups all equal values in one pass, so the same input costs $n$ comparisons and one frame.

The lesson is that randomization fixes the adversarial order but not a bad partition. A random pivot on an all-equal array still chooses a valid pivot, and a two-way partition still degrades. The partition rule and the pivot rule are separate decisions.

## Variants and extensions

- Two-way Lomuto partition. The simplest partition, with one cursor and one boundary. It is correct with a random pivot but quadratic on duplicate-heavy input.
- Two-way Hoare partition. Faster in practice than Lomuto because it performs fewer swaps, but the boundary conventions are easy to get wrong.
- Median-of-three randomized pivot. Sample three random positions and use their median. The pivot is closer to the center on average, at the cost of two extra generator draws and three comparisons.
- Dual-pivot quicksort. Partition around two pivots into three blocks. Java's primitive sort uses this variant, and it is faster than single-pivot quicksort on many real inputs.
- Introsort. Randomized or median-of-three quicksort with a depth counter and a heapsort fallback. This is the standard library compromise between expected speed and worst-case safety.
- Block quicksort. Partition into blocks and buffer the swaps, which reduces branch mispredictions. It is a performance variant, not a different algorithm.
- Randomized quickselect. Recurse into only the side that contains the wanted rank. The expected time is linear and the worst case is quadratic. It is the selection counterpart of this article.
- Fisher-Yates shuffle. The standard way to put an array into a uniformly random order. It is the preprocessing step for randomized incremental algorithms and for the shuffle-then-sort baseline.
- Reservoir sampling. Keep a uniform sample of $k$ items from a stream of unknown length. It is the streaming version of the random position idea.
- Random sampling for heavy hitters. Sample positions, verify the sampled values with exact counts, and use a union bound over the at most $k - 1$ values above the threshold.
- Randomized incremental construction. Insert the points of a geometric problem in random order and repair the structure when a new point violates it. The smallest enclosing circle is the canonical example.
- Treap. A binary search tree with a random priority per node. The priorities make the tree shape a random binary search tree, so the expected height is $O(\log n)$.
- Randomized hashing. Choose the hash function from a family after the input is known. An adversary who does not know the function cannot force collisions, which is the defense against hash-table denial of service.
- Miller-Rabin and Pollard rho. Monte Carlo algorithms for primality and factorization. They are covered in their own articles, but they follow the same pattern: a random choice, a deterministic check, and a bound on the error probability.
- Derandomization. Replace the random choices with a deterministic construction that has the same guarantee. Median of medians replaces a random pivot in selection, and deterministic expanders replace random ones in some hash families. Derandomization usually costs a larger constant or more complex code.

## Contest strategy

1. Decide whether the problem needs randomization at all. If a deterministic algorithm fits the limits, use it; a hard guarantee is easier to defend than a probabilistic one.
2. If the problem is a sort, use the standard library unless the statement asks for a specific pivot, a comparison count, or a custom partition. The library sort is faster and has a worst-case fallback.
3. Seed the generator from an unpredictable source in a submission. `std::chrono::steady_clock::now().time_since_epoch().count()` or `std::random_device` is enough to defeat precomputed tests. Use a fixed seed only in a reference implementation or a test.
4. Do not use `rand()` for anything that needs more than a few thousand distinct values. Its range is small on many platforms, and its low bits are poor. A 32-bit xorshift or splitmix64 is short and adequate.
5. Handle duplicates with a three-way partition. If the values are known to be distinct, a two-way partition is fine; if the statement does not guarantee distinctness, assume duplicates.
6. Count comparisons in 64 bits. A quadratic run overflows a 32-bit counter at a size that is easy to reach.
7. Guard the recursion. Use introsort or the smaller-side-first rule if the input can be adversarial and the language stack is small. Python and JavaScript are the most fragile.
8. Verify every Monte Carlo candidate. Sample, then count or check with a deterministic routine. Never print a sampled value without verification.
9. State the complexity correctly: expected time, worst-case time, and the failure probability for a Monte Carlo algorithm. "Expected $O(n \log n)$" is not the same claim as "$O(n \log n)$".
10. Test the edge cases: $n = 1$, all equal, sorted, reverse sorted, negative values, and a value repeated at both ends. The fixed-seed fixtures are a good start, but a real submission should also be compared with a deterministic sort on random arrays.

## Worked problems

### Problem 1: Ghd

**Restatement.** Given $n$ values, find the largest positive integer $g$ that divides at least half of them.

**Naive baseline.** Enumerate every divisor of every value, count how many values each divisor divides, and take the largest that reaches half. A value near $10^{12}$ has a few thousand divisors, and there are $n$ values, so the candidate set is large and the counting is worse. Testing each candidate against all $n$ values is far beyond the limits.

**Insight.** The answer divides at least half of the values, so a uniformly random value is divisible by the answer with probability at least $1/2$. If the sampled value is $x$, the answer is one of the divisors of $x$. One sample reduces the candidate set from every divisor of every value to the divisors of one value.

**Derivation.** Repeat the following about 20 times. Sample an index and let $x$ be its value. For every array value $a_j$, compute $g_j = \gcd(x, a_j)$ and count how often each gcd occurs. A divisor $d$ of $x$ divides $a_j$ exactly when $g_j$ is a multiple of $d$. For every divisor $d$ of $x$, sum the counts of the gcd groups that are multiples of $d$, and update the best answer when the sum is at least half of $n$.

**Correctness.** If the sampled $x$ is one of the values divisible by the true answer $g^{\ast}$, then $g^{\ast}$ divides $x$, so it appears in the divisor list. The gcd grouping is exact: $d$ divides $a_j$ if and only if $d$ divides $\gcd(x, a_j)$, because $d$ divides $x$. The count for $g^{\ast}$ is therefore exactly the number of values divisible by $g^{\ast}$, which is at least half. The only failure is that every one of the 20 samples misses the divisible half, which happens with probability at most $2^{-20}$.

**Complexity.** Each sample costs $O(n \log A)$ for the gcds, where $A$ is the largest value, plus the divisor grouping. The grouping is proportional to the number of divisors of $x$ times the number of distinct gcd values; both are small compared with $n$ for values below $10^{12}$. With 20 samples the total is practical for $n = 10^6$.

**Common wrong approach.** Enumerating the divisors of the sampled value and testing each divisor against every array value. That is correct but too slow. A second error is returning the largest divisor of the sample without checking its count; the largest divisor is the sample itself, and it need not divide half the array.

### Problem 2: Cut and Stick

**Restatement.** Given an array of $n$ values and $q$ ranges $[l, r]$, partition each range into the minimum number of subsequences such that no piece of length $x$ contains a value more than $\lceil x/2 \rceil$ times.

**Naive baseline.** For each query, scan the range, count every value in a hash map, find the maximum frequency $f$, and apply the formula below. The scan costs $O(n)$ per query, or $O(nq)$ overall, which is too slow at $3 \ast 10^5$ for both $n$ and $q$.

**Insight.** The answer depends only on the length $L = r - l + 1$ and the maximum frequency $f$ in the range: the minimum number of pieces is $\max(1, 2f - L)$. If $f \le L/2$, one piece is beautiful because no value exceeds half of it. If $f > L/2$, the copies of the mode cannot all share pieces with the other values, and the excess $2f - L$ is exactly the number of pieces forced.

**Derivation.** Store the sorted positions of each value. A value's count in $[l, r]$ is the difference of two binary searches in its position list. For each query, draw $R$ random positions from $[l, r]$, deduplicate the sampled values, count each one exactly, and keep the largest count $f$ found. If $f > L/2$, the answer is $2f - L$; otherwise the answer is $1$. When the true mode is a strict majority, it is unique and a random position hits it with probability above $1/2$, so $R = 40$ samples miss it with probability below $2^{-40}$.

**Correctness.** For a lower bound, let a piece contain $x_i$ copies of the mode and $y_i$ other values. The beauty condition gives $x_i \le y_i + 1$, because $x_i \le \lceil (x_i + y_i)/2 \rceil$. Summing over the pieces gives $f \le (L - f) + P$, so $P \ge 2f - L$, and at least one piece is always needed. The bound is attainable: start with $2f - L$ pieces, each holding one copy of the mode, pair each of the remaining $L - f$ copies with one of the $L - f$ other values, and add the pairs to those pieces. Every piece then has one more mode copy than other values, so the minimum is $\max(1, 2f - L)$. If the true $f$ is at most $L/2$, the formula gives $1$ and the sampled maximum also gives $1$, because no sampled count can exceed $L/2$. If the true $f$ is above $L/2$, it is the unique mode, and the only failure is that all $R$ samples miss it. Every sampled candidate is verified exactly, so a false positive is impossible.

**Complexity.** Preprocessing the position lists costs $O(n \log n)$ or $O(n)$ with counting sort. Each query costs $O(R \log n)$ for the binary searches, with $R$ a constant chosen for the error target. The space is $O(n)$.

**Common wrong approach.** Returning $-1$ when no sampled value exceeds the threshold. That is the answer shape of a different query; here the answer is $1$ whenever the maximum frequency is at most $L/2$. A second error is returning $2f - L$ without the maximum with $1$, which produces zero or a negative number on a balanced range. A third is sampling a single position and trusting it without counting.

### Problem 3: Minimum Circle Cover

**Restatement.** Given $N$ points in the plane with coordinates of at most two decimal places, find the smallest circle that contains all of them. Output the radius on the first line and the center coordinates on the second line, with an absolute error at most $10^{-9}$. The limits are $N \le 10^5$ and $|x_i|, |y_i| \le 10^4$.

**Naive baseline.** Enumerate every triple of points, build its circumcircle, test whether it contains all points, and keep the smallest circle that does. The cost is $O(n^4)$ in the obvious form, or $O(n^3)$ with careful filtering. Both are far too slow for $10^5$ points.

**Insight.** Insert the points in a uniformly random order and maintain the smallest circle of the prefix. When a new point lies outside the current circle, the new circle must have that point on its boundary. Fix the point and rescan earlier points; when a second point violates the circle, the new circle must pass through both. Fix both and rescan again; when a third point violates, the circle through the three points is forced.

**Derivation.** Shuffle the points. Start with the circle through the first point, with radius zero. For each point $p_i$, if it is outside the current circle, rebuild: set the circle to the point $p_i$ with radius zero, scan $p_0, \ldots, p_{i-1}$, and when $p_j$ is outside, set the circle to the diameter of $p_i$ and $p_j$; scan $p_0, \ldots, p_{j-1}$, and when $p_k$ is outside, set the circle to the smallest circle through $p_i$, $p_j$, and $p_k$. If the three points are collinear, the smallest circle is the diameter of the farthest pair. The containment test uses squared distances with an epsilon, and the final output prints the radius before the center.

**Correctness.** The invariant is that the current circle is the smallest circle of the points processed so far. If a new point is inside, the circle stays minimal. If it is outside, every circle that contains the prefix and the new point must have the new point on its boundary, so fixing it is safe. The same argument applies to the second and third violations: each violating point is forced onto the boundary of the new minimal circle. The innermost rebuild returns the smallest circle through the three boundary points, so the invariant is restored after each repair.

**Complexity.** The expected number of times the $i$-th point changes the boundary is at most $3/i$, because a random prefix has at most three boundary points and each is equally likely to be the last inserted. Summing $3/i$ over the points gives $O(\log n)$ expected boundary changes, and the nested rescans make the total expected work $O(n)$. The worst case is $O(n^3)$ if the random order is unlucky, but the probability is negligible. The space is $O(n)$ for the points.

**Common wrong approach.** Skipping the shuffle. A sorted or adversarial insertion order can force a boundary change at every point, and the nested loops then approach cubic time. A second error is using the circumcircle formula on collinear points, where the determinant is zero; the diameter fallback is required. A third is comparing floating-point distances without an epsilon, which can classify a point on the boundary as outside and rebuild forever on nearly degenerate input. A fourth is printing the center before the radius, which the checker rejects even when the geometry is correct.

## Practice progression

1. Recognition. Given a statement, decide whether it needs a correct answer with a random running time (Las Vegas) or a fast answer with a small error probability (Monte Carlo). The distinction determines what must be verified.
2. Direct application. Implement randomized quicksort with a fixed seed, compare its output with `std::sort` on every permutation of six small values, and record the comparison count for each permutation.
3. Adaptation. Replace the two-way partition with the three-way partition and run both versions on an array of ten thousand equal values. The two-way version should show quadratic comparisons and deep recursion; the three-way version should finish in one pass.
4. Combination. Use the same generator for randomized quickselect, select the median, and compare the comparison counts with a full randomized sort. The selection should be linear in expectation.
5. Challenge. Implement random sampling for a frequent-value query, measure the miss rate over many seeds, and compare it with the union bound. Then implement the smallest enclosing circle with and without the shuffle and compare the running times on a convex position set.
6. Transfer. Implement a treap with random priorities, a randomized hash table, and Miller-Rabin. All three use the same pattern: a random choice that removes an adversarial structure, a deterministic check, and an expected or high-probability bound.
